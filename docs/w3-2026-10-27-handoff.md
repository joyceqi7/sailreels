## 权益与财务边界

- `TTMinis.createSubscription` / `reactivateSubscription` 回调只触发查单。平台查单即使返回 `SUCCESS`，也不会绕开签名 Webhook 直接发权益。
- Cancel 只关闭续费，剩余权益由 `rights_valid` 与 `benefit_end_time` 决定；OnHold 保留已确认的剩余权益。Expire / Revoke 关闭权益。
- 历史 Refund 仅更新原扣款记录；当前期 Revoke 立即关闭订阅。晚到 Create / Renew 不能复活已撤销或已过期的合同。
- 每订阅保存平台事件时间；同秒歧义按保守优先级收敛，撤销/过期优先。**同秒先后无可靠平台序列号，无法保证完全重建平台时间线**，真机联调需确认；原始事件保留供查账。
- Create 必须有明确 `is_sandbox` 布尔值，后续事件不能改变已绑定合同的测试分类。生产环境禁止测试权益和测试档位，即便错误打开测试配置也不放行。
- 钱包展示本应用订单，`beans_balance` 返回 `null`。没有平台余额接口证据时不虚构余额；此页不是平台资金结算报表。
- 重新登录切换 TikTok 账号后，不把前一账号的购买/进度请求重放到新账号。进度写入队列同样检查账号归属。

2. 执行 `uv run alembic upgrade head`，新 head 为 `90a3c8d2e641`。新增订阅支付记录表、事件顺序列、订单状态列，原观看进度表复用。

4. 正式商品批准后配置 `SUBSCRIPTION_TIER_IDS=["实际正式TierID"]`。正式价格/周期从平台查询，前端不自定价格；无正式档位时显示暂不可用。
5. 前端构建设置 `VITE_API_MODE=live` 与实际 HTTPS API 地址。默认 mock 仅用于本地预览，没有真实登录、支付或平台券。
6. Webhook 沿用 `/api/v1/webhooks/tiktok`，必须保持支付 2 类 + 订阅 8 类全部订阅；运行已有 beat 重试扫描，监控重试耗尽事件。

迁移会把已关联合同的历史 **create** 订单标记为 confirmed；旧版本 reactivate 无法仅由非空合同 ID 判断是否已完成，保留待核查。新财务记录不伪造历史金额；已有八类原始 Webhook 可由运营核对并安排回填。未知平台订单、缺少平台订单号的超时订单必须核实后处理，不能因超时自动解除购买保护。
